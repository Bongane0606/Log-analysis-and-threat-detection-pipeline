# SSH Log Analysis and Threat Detection Pipeline

A small end-to-end security pipeline that parses SSH authentication logs,
loads them into a database, runs detection rules against them to flag
suspicious activity (brute-force and password-spraying attacks), and
displays the results on a live dashboard.

This was built for my cybersecurity elective. All attacks were generated
against my own local, isolated test environment — nothing here was ever
run against a system I don't own.

---

## 1. What this project does

```
auth.log  →  parse_ssh.py  →  events.db (ssh_events table)
                                     │
                                     ▼
                              detect_ssh.py
                                     │
                                     ▼
                        events.db (alerts table)
                                     │
                                     ▼
                              dashboard.py  →  browser dashboard
```

1. **`parse_ssh.py`** reads raw OpenSSH log lines (from `/var/log/auth.log`
   or `journalctl -u ssh`), extracts the relevant fields (timestamp, host,
   user, source IP, and whether the login succeeded, failed, or targeted a
   nonexistent user), and loads them into a SQLite database (`events.db`,
   table `ssh_events`).

2. **`detect_ssh.py`** reads `ssh_events` and applies two detection rules:
   - **Brute force:** 5 or more failed login attempts from a single IP
     within a 5-minute sliding window.
   - **Password spraying:** 4 or more *distinct usernames* attempted from
     a single IP within a 10-minute sliding window.

   Any matches are written to an `alerts` table in the same database.

3. **`dashboard.py`** is a Streamlit app that reads `events.db` and shows:
   - summary metrics (total events, failed/successful logins, alert count)
   - a table of all alerts raised
   - a line chart of events over time (failed / success / invalid user)
   - a bar chart of the top offending IPs
   - the raw, searchable event log

---

## 2. Why it's built this way

- **SQLite** instead of flat files or a bigger database server — it needs
  zero setup, keeps everything in one portable `events.db` file, and is
  easy to query directly (`sqlite3 events.db`) for debugging or marking.
- **A sliding time window** (rather than fixed-size buckets, e.g.
  "per calendar minute") because an attack can start at any point in
  time; a sliding window catches a burst wherever it falls in the log.
- **One alert per burst, not per failed attempt** — otherwise a single
  12-attempt brute-force run would generate 8 separate alerts instead of
  one meaningful one.
- **Streamlit for the dashboard** — it turns a SQL table into a working
  web dashboard with almost no front-end code, which kept the project
  focused on the detection logic rather than UI plumbing.

## 4. How to set up and run it

### 4.1 One-time setup

Clone the repo, then from inside the project folder:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

- `python3 -m venv venv` creates an isolated Python environment so this
  project's dependencies don't clash with anything else on the system.
- `source venv/bin/activate` switches your shell into that environment
  (your prompt will show `(venv)` once it's active). **Run this every
  time you open a new terminal to work on the project.**
- `pip install -r requirements.txt` installs Streamlit, pandas, and
  anything else the project needs.

### 4.2 Setting up the test SSH target (optional — only if regenerating logs)

The logs I analyzed came from a local SSH server restricted to
`127.0.0.1`, so it was never reachable from the network:

```bash
sudo apt install openssh-server
echo "ListenAddress 127.0.0.1" | sudo tee /etc/ssh/sshd_config.d/lab.conf
sudo systemctl restart ssh
ss -tln | grep ':22'     # confirms it's listening only on 127.0.0.1
sudo adduser labuser     # throwaway account, not a real user
```

Attacks were then run against `127.0.0.1` only, using Hydra (fast
brute force / spraying) and a custom `sshpass` loop (slow, evasive
brute force — see `attack-journal.md` for exact commands and times).

**This step is not required to run the pipeline** — it's only needed if
you want to regenerate fresh logs from scratch rather than reuse mine.

### 4.3 Get the logs into the project folder

```bash
sudo journalctl -u ssh --no-pager -o short > auth.log
```

This exports the SSH service's log history in the plain-text format the
parser expects. (If your system writes a traditional `/var/log/auth.log`
file instead, you can use that directly.)

### 4.4 Run the pipeline

```bash
python3 parse_ssh.py auth.log
```
Parses the log and loads structured events into `events.db`. Prints how
many events were loaded.

```bash
python3 detect_ssh.py
```
Runs the brute-force and password-spraying rules against those events
and writes any alerts to `events.db`. Prints each alert found.

```bash
streamlit run dashboard.py
```
Starts the dashboard. It opens automatically in your browser (usually
at `http://localhost:8501`). Press `Ctrl+C` in the terminal to stop it.

If you re-run `parse_ssh.py` / `detect_ssh.py` while the dashboard is
already open, just refresh the browser tab to see the updated data.

## 5. Results

See `attack-journal.md` for the full list of attacks run, with timestamps.

**Summary:**
- The brute-force rule correctly caught a fast Hydra wordlist attack
  (12 failed attempts within seconds).
- The password-spraying rule correctly caught a Hydra run trying 6
  different usernames with one password.
- A manual, legitimate login (two mistyped passwords followed by a
  correct one) was **not** flagged, confirming the rules don't trigger
  on ordinary user error.
- A slow brute-force attack (8 attempts spaced ~90 seconds apart) was
  **not** caught, because it never produced 5 failures inside any single
  5-minute window.

### Known limitation

The last result above is a deliberate finding, not a bug: a patient
attacker who paces their attempts below the rule's threshold can evade
detection. A production system would need additional defenses for this,
such as:
- a longer-window, lower-threshold secondary rule (e.g. 8 failures in
  30 minutes) to catch slower attacks without raising false positives
  on normal typos,
- rate limiting or account lockout at the SSH server level
  (e.g. `fail2ban`) independent of log analysis,
- baselining normal failed-login rates per IP/user over a longer period
  and flagging statistical deviations rather than fixed thresholds.
